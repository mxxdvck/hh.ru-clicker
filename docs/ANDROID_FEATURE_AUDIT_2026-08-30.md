# Аудит функций Android-приложения HH — 2026-08-30

## Область и источники

- Официальная карточка `ru.hh.android` в RuStore: версия **26.32**, дата
  публикации **2026-08-25**, размер 57.1 MB, Android 8+.
- Официальная карточка Google Play: обновлено **2026-08-26**.
- Официальная история App Store использована только как подтверждение темпа и
  состава релизов 26.29–26.32; сетевые контракты Android из неё не выводились.
- Код проекта и ранее выполненный статический разбор Android 26.28.1/26.29,
  отражённый в `HH_API_MAP.md`, `docs/API_REFERENCE.md` и `app/mobile_*`.

Свежий бинарник 26.32 не был доступен для прямой загрузки из официальных
web-карточек без клиента магазина. Поэтому утверждать, что все новые приватные
endpoint'ы 26.30–26.32 извлечены, нельзя. Ниже отдельно разделены подтверждённые
функции и выводы из старого APK.

## Главный вывод

Нет, все возможности Android-приложения в clicker не перенесены. Основной
автоматизированный сценарий (поиск → проверка → отклик → анкета/письмо,
переговоры, резюме и статистика) покрыт хорошо. Однако значимая часть функций
приложения либо используется только внутри движка, либо не имеет GUI, либо не
реализована.

Кроме того, mobile-протокол проекта отстаёт от официального релиза на три
версии и использует несовместимые между собой значения версии:

| Место | Текущее значение |
|---|---|
| `app/hh_mobile_transport.py` | `ru.hh.android/26.29.11476` |
| `app/mobile_auth.py` | `app_version_name=26.29` |
| `app/user_agent.py` | `APP_VERSION_NAME=26.28.1` |
| `app/ws_client.py` и несколько routes | `ru.hh.android/26.28.1` |
| Официальный актуальный релиз | `26.32` |

Это не доказанный runtime-баг: сервер может принимать старые версии. Но это
реальный источник расхождений A/B-конфигурации, capability flags и диагностики.
Обновлять номер вслепую нельзя — сначала нужен бинарный diff 26.29 → 26.32 и
read-only probe.

## Что полезно перенести в первую очередь

1. **Центр уведомлений HH**: список, тип события, переход к вакансии/чату,
   пометка прочитанным. Сейчас realtime-события принимаются, но теряются как
   самостоятельный пользовательский объект.
2. **Избранное и сохранённые поиски в GUI**: данные уже читаются backend'ом;
   сначала безопасный read-only экран, затем создание/удаление после проверки
   контрактов.
3. **Полное управление видимостью резюме** с явным предпросмотром последствий.
   Это напрямую влияет на возможность отклика и обнаружимость работодателями.
4. **Жалоба на вакансию** и отображение признаков проверенного работодателя —
   полезно для безопасности автоматического режима.
5. **Завершение skill verification и employer review flows**: UI уже начат,
   поэтому стоимость доведения ниже, чем у карты или звонков.
6. **Карта вакансий** — только если важен географический поиск; для массового
   автоматического отклика ценность ниже фильтров расстояния/метро.

## Что не стоит копировать буквально

- Встроенные звонки, карьерные статьи, Mentors/Skills microfrontends и магазин
  платных услуг не относятся к ядру автоматического отклика.
- Push-инфраструктуру Android лучше не эмулировать. Для web-приложения надёжнее
  нормализовать уже получаемые WebSocket-события и показывать собственный inbox.
- Номер версии Android нельзя просто заменить на 26.32 во всех заголовках:
  package build code, набор обязательных заголовков и feature flags должны быть
  подтверждены свежим APK.

## Следующий технический этап

1. Получить 26.32 из официального RuStore-клиента или Google Play account.
2. Проверить подпись пакета и сохранить SHA-256, versionCode/versionName.
3. Выполнить endpoint/string diff относительно 26.28.1/26.29.
4. Сверить auth headers, WebSocket handshake и remote-config keys.
5. Делать только read-only live probes; write-контракты покрывать fixtures до
   отдельного разрешения на проверку в аккаунте.
